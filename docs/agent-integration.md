# Внедрение проверки ответов по документам в агентский цикл

Инструмент «Ответы по документам» можно подключить к существующему AI-приложению на двух уровнях. Если приложение уже само читает документы и генерирует ответы, добавьте локальный валидатор перед отправкой ответа. Если приложение умеет делегировать задачи инструментам, подключите весь сценарий `verified`. Он прочитает документы, вызовет настроенную модель, проверит ответ и сохранит отчёт.

| Что умеет существующая система | Что подключить |
| --- | --- |
| Управляет моделью, документами и повторными попытками | `validate_answer` как шаг агентского цикла |
| Вызывает инструменты и получает результаты | `run_query` за адаптером вызова |
| Работает отдельно и поддерживает MCP | Локальный MCP-сервер, который передаёт запросы модели клиента и проверяет её ответы |

## Локальный MCP-сервер

MCP работает локально по **STDIO**. Клиент запускает Python-процесс и общается с ним через стандартные потоки. Команду установки и пример конфигурации можно скопировать на странице **Подключение MCP** в дашборде.

### Подготовка

Из корня проекта установите зависимости. Если окружение ещё не создано, сначала выполните `.\src\setup.ps1`.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-mcp.txt
```

На Linux и macOS создайте окружение через `python3 -m venv .venv` и используйте `.venv/bin/python`. Для PDF дополнительно установите `requirements-pdf.txt`.

Ответы генерирует модель подключённого MCP-клиента. Для этого режима не требуется настраивать `BASE_URL`, `MODEL` или `API_KEY` в проекте. Подключение модели и её разрешения настраиваются в самом клиенте. CLI и обработка через дашборд используют настройки API из `.env`.

### Подключение клиента

В MCP-клиенте на той же машине добавьте сервер с именем `document-agent` и транспортом **STDIO**. Команда — абсолютный путь к Python из `.venv`, единственный аргумент — абсолютный путь к `run_mcp.py`. Клиент сам запускает и завершает процесс. Не запускайте сервер заранее в отдельном терминале.

Пример для Windows и клиента с разделом `mcpServers`. Замените `C:/projects/document-agent` в обоих путях на свою папку проекта. Если раздел уже есть, добавьте в него запись `document-agent`.

```json
{
  "mcpServers": {
    "document-agent": {
      "command": "C:/projects/document-agent/.venv/Scripts/python.exe",
      "args": ["C:/projects/document-agent/run_mcp.py"]
    }
  }
}
```

На Linux и macOS используйте абсолютные пути вида `/home/user/document-agent/.venv/bin/python` и `/home/user/document-agent/run_mcp.py`. Рабочую папку клиента настраивать не нужно. Если раньше использовали URL, замените старую запись конфигурацией STDIO и переподключите сервер.

Для диагностики доступна команда `python run_mcp.py --help`. Запуск `python -m src.mcp_server` из корня проекта тоже использует STDIO. Прогресс и журнал направляются в `stderr`, `stdout` занят протоколом. [Транспорт STDIO в спецификации MCP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#stdio).

Тексты выбранных документов и вопросы передаются модели MCP-клиента. Если клиент использует облачную модель, документы обрабатываются её провайдером. Сам сервер MCP не делает HTTP-запросов генерации. Дождитесь завершения обработки до отключения клиента.

Для проверки связи попросите клиента вызвать `list_document_sets` через `document-agent` и показать список комплектов. В нём должен появиться `P01`. Затем задайте проверочный вопрос по `P01` или прикрепите свои документы и задайте вопрос по вложениям текущего чата.

| Инструмент | Параметры и результат |
| --- | --- |
| `create_document_chat` | Создаёт пустой файловый контекст и возвращает `chat_id`. Клиент сохраняет его в текущем разговоре. |
| `get_document_chat` | По `chat_id` показывает имена и `attachment_id` загруженных вложений. |
| `list_document_sets` | Возвращает ID, названия и имена файлов в сохранённых комплектах, включая `P01`–`P06`. |
| `upload_documents` | Принимает `files` со списком объектов `{name, content_base64}`. С `chat_id` добавляет файлы к прежним вложениям чата. С `title` создаёт отдельный комплект и возвращает `document_set_id`. |
| `ask_documents` | Принимает `chat_id` или `document_set_id` и список `questions`. Для чата можно указать `attachment_ids`. Возвращает `run_id`, состояние и запрос модели клиента. |
| `submit_document_response` | Принимает `run_id`, `request_id`, JSON-ответ модели строкой `response` и, для чата, `chat_id`. Проверяет ответ и возвращает следующий запрос или итог. |
| `get_document_run` | Принимает `run_id` и, для запуска из чата, тот же `chat_id`. Возвращает ожидающий запрос модели или готовые ответы с цитатами. |

### Генерация и исправления через MCP

Сервер и агент обмениваются запросами и ответами через обычные инструменты MCP. Отдельная поддержка MCP Sampling клиентом не требуется. MCP всегда использует строгий режим `verified`: проверку цитат, чисел и дат, разбиение вопросов и сохранение отчёта. Переключить его на `baseline`, отключить проверку или выбрать внешний API через MCP нельзя. Настройки генерации из `.env` в этот режим не попадают.

Управление запусками MCP находится в отдельном модуле и не использует фоновые задачи дашборда. Существующий конвейер получает модель агента явно; загруженные файлы и результаты хранятся в `runs/.agent/`.

1. Агент вызывает `ask_documents`. Сервер делает снимок выбранных файлов и готовит запрос.
2. При `status=requires_response` агент выполняет `model_request.messages` своей моделью. Запрос содержит правила, документы, вопросы и, при исправлении, предыдущие ответы с ошибками проверки. Инструкции внутри документов считаются недоверенными данными.
3. Агент вызывает `submit_document_response`, передавая `request_id` из этого запроса и JSON-ответ строкой `response`. Для чата во всех вызовах сохраняется тот же `chat_id`.
4. Сервер проверяет ответ. Для неподтверждённых ответов выдаётся новый запрос на исправление, максимум два исправления. После исчерпания попыток сохраняется «не знаю». Следующая группа вопросов также возвращается как `requires_response`.
5. При `running` агент запрашивает `get_document_run`. При `completed` или `completed_with_errors` показывает сохранённые `answers`, включая причины технических отказов. Черновики до проверки не выдаются за итоговый ответ.

JSON и повторы обрабатывает агент, пользователю достаточно обычного вопроса. Ответ привязан к конкретному `request_id`; устаревший или повторный ответ отклоняется. На один ответ клиента отводится 15 минут. После перезапуска MCP незавершённый запрос нужно начать заново через `ask_documents`; файлы чата и завершённые результаты сохраняются. Расход токенов учитывает клиент, сервер записывает количество запросов к нему.

После обновления сервера переподключите MCP, чтобы клиент получил инструмент `submit_document_response` и новые инструкции.

### Файлы в текущем чате

При первой загрузке клиент создаёт `chat_id` и использует его для следующих вложений и вопросов. Перед вопросом клиент находит подходящие вложения в текущем разговоре, включая предыдущие сообщения, и передаёт доступные байты через `upload_documents`. Повторная передача файла с тем же именем и содержимым использует уже сохранённое вложение. Для конкретной задачи клиент передаёт `attachment_ids`, полученные от `get_document_chat`. Если аргумент опущен, в обработку попадают все файлы этого чата. Для нового разговора клиент создаёт отдельный пустой контекст.

Для загрузки по MCP клиент передаёт байты вложения в `content_base64`. Допустимо до 500 файлов и 80 МиБ на загрузку или обработку, до 20 МиБ на файл. Извлечённый текст должен помещаться в контекст модели. Если клиент не передаёт байты вложений, попросите его создать чат и показать `chat_id`, затем добавьте файлы командой из корня проекта.

```powershell
.\run.ps1 upload-documents --chat-id "<chat_id>" --attachment "Договор.docx" "Условия.txt"
```

Файлы чата сохраняются в `runs/.agent/chats/<chat_id>/`, отдельные комплекты — в `runs/.agent/documents/`. После перезапуска продолжить работу с чатом можно по сохранённому `chat_id`.

Чтобы проверить подключение, спросите в чате, какой способ определения поставщика указан в извещении P01. Ожидается «Электронный аукцион» с цитатой из `01_izveshchenie.txt`.

## Проверка внутри существующего агентского цикла

Подключите [`validate_answer`](../src/generation/validation.py) перед узлом, который публикует ответ. Передавайте ему черновик и карту `имя источника → извлечённый текст`. Имена в `evidence[].file` должны совпадать с ключами этой карты. Для чтения файлов можно использовать существующий [`load_documents`](../src/files/input_loader.py) и передать из результата `documents` и `read_errors`.

1. Получите структурированный черновик от модели. Для фактического ответа нужны `status`, `answer` и `evidence` со списком объектов `file` и `quote`. Для расхождения нужны подтверждающие цитаты как минимум из двух файлов.
2. Вызовите `validate_answer(draft, documents, read_errors)`. Валидатор проверяет наличие цитаты в указанном файле и подтверждение чисел, дат и времени, которые он распознал. Он также проверяет поддерживаемый расчёт процентов, если черновик содержит поле `calculation`.
3. Если есть ошибки, передайте черновик и список ошибок обратно в узел генерации. Сохраняйте тот же набор источников между попытками. После двух исправлений выдайте `не знаю`, если ошибки остались.
4. Показывайте итоговый ответ и его источники. Статус `нет в документах` допускается при наличии читаемых документов и отсутствии ошибок чтения. Его смысл зависит от полноты поиска. Пустой список ошибок валидатора подтверждает прохождение этих проверок. Применимость редакции документа и полноту ответа оценивает агент.

### Рабочий пример без вызова модели

Запустите пример из корня проекта в окружении Python проекта. Функция `repair` в примере имитирует исправление. В агенте замените её своим вызовом модели с исходным вопросом, документами, черновиком и ошибками проверки.

```python
from src.generation.validation import norm, validate_answer


def review_answer(draft, documents, read_errors, repair, max_repairs=2):
    if max_repairs < 0:
        raise ValueError("Число исправлений должно быть неотрицательным.")

    for remaining in range(max_repairs, -1, -1):
        errors = validate_answer(draft, documents, read_errors)
        if not errors:
            status = norm(draft["status"])
            if status in ("не знаю", "нет в документах"):
                return {"status": status, "answer": "", "evidence": []}
            return {
                "status": status,
                "answer": draft["answer"],
                "evidence": [
                    {"file": item["file"], "quote": item["quote"]}
                    for item in draft["evidence"]
                ],
            }
        if remaining:
            draft = repair(draft, errors)

    return {"status": "не знаю", "answer": "", "evidence": []}


quote = "Срок поставки составляет 30 календарных дней."
documents = {"contract.txt": quote}
draft = {
    "status": "ответ",
    "answer": "Срок поставки составляет 45 календарных дней.",
    "evidence": [{"file": "contract.txt", "quote": quote}],
}


def repair_example(previous, errors):
    assert any("45" in error for error in errors)
    return {**previous, "answer": quote}


result = review_answer(draft, documents, [], repair_example)
assert result["status"] == "ответ" and result["answer"] == quote

rejected = review_answer(draft, documents, [], repair_example, max_repairs=0)
assert rejected["status"] == "не знаю"
```

В существующем графе LangGraph добавьте узел проверки после узла генерации. В состоянии графа храните черновик, ссылку на снимок источников, ошибки и число использованных исправлений. Через `add_conditional_edges` направляйте прошедший ответ в узел публикации, исправимый черновик обратно в генерацию, а после исчерпания бюджета переходите в узел осторожного отказа. На один вопрос выделяйте общий бюджет цикла, включая повторы, которые может делать сам агент. [Документация LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api#conditional-edges)

## Подключение всего режима verified как инструмента

Этот вариант подходит, если основная система делегирует обработку документов. Используйте [`run_query`](../src/workflows/query.py), который уже вызывают CLI и дашборд. Он возвращает код завершения и сохраняет структурированные ответы с цитатами в `answers.json`, а отчёт в `report.html`. Для генерации настройте `BASE_URL`, `MODEL` и `API_KEY` по [README](../README.md#настройте-модель).

Пример адаптера для доверенного Python-бэкенда. До вызова бэкенд должен сопоставить идентификаторы вложений с разрешёнными локальными файлами. `runs_dir` задаёт бэкенд. Эта папка должна существовать.

```python
from pathlib import Path
from uuid import uuid4

from src.settings import QueryOptions
from src.workflows.query import run_query


def answer_from_documents(document_paths, questions, runs_dir):
    run_id = uuid4().hex
    output = Path(runs_dir).resolve() / run_id

    run_query(
        QueryOptions(
            attachment=[str(path) for path in document_paths],
            prompt=questions,
            mode="verified",
        ),
        output=output,
    )

    artifacts = {
        "answers.json": "Структурированные ответы и цитаты.",
        "answers.csv": "Таблица ответов.",
        "report.html": "Отчёт для просмотра в браузере.",
        "manifest.json": "Статус, настройки и статистика запуска.",
        "inputs.json": "Вопросы и извлечённый текст источников.",
        "prompts.json": "Системные инструкции режимов ответа.",
        "progress.log": "Хронология обработки.",
        "trace.jsonl": "Подробные события проверки и исправлений.",
    }
    return [
        {"path": str(output / name), "description": description}
        for name, description in artifacts.items()
        if (output / name).is_file()
    ]
```

Для внешнего инструмента используйте контракт `document_ids` и `questions` на входе. Передавайте файлы запуска с описаниями, чтобы следующий шаг мог выбрать нужные артефакты. Если агент работает на другом хосте, заменяйте локальные пути ссылками на выдачу файлов с проверкой доступа. Ошибки чтения, конфигурации или запуска переводите в явный статус ошибки. Для длительных обработок разделите интерфейс на запуск и получение файлов по `run_id`. В существующем бэкенде эти операции можно зарегистрировать как функции агента, а при поддержке MCP представить как инструменты. [Спецификация MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

HTTP-маршруты дашборда обслуживают локальный браузер. Для общей AI-системы размещайте адаптер за её авторизацией. Проверяйте права на документы и отчёты при каждом обращении, храните ключ модели на сервере и отправляйте провайдеру только разрешённые документы. Отображайте ссылки через сервер выдачи артефактов с проверкой прав по `run_id`.

### Итоговая оценка по эталону

Итоговая оценка доступна в разделе **Тестовые наборы**. Сценарий запуска передаёт путь к эталону через внутренний параметр `evaluation_data`. По обычному запросу `query` применяется выбранный режим ответа. [Код сопоставления с эталоном](../src/evaluation/query_evaluation.py)

## Что развить после подключения

| Возможность | Что добавить | Как проверить пользу |
| --- | --- | --- |
| Переход к источнику | Сохранять номер страницы или абзаца и версию файла рядом с цитатой. В чате открывать соответствующее место в документе. | Доля цитат, которые открываются в нужном месте. |
| Работа с большими комплектами | Перед генерацией искать релевантные фрагменты. Для проверки сохранять их связь с исходным текстом и учитывать пропущенные разделы. | Сравнивать полноту нахождения известных цитат и объём контекста на одном наборе вопросов. |
| Разбор расхождений и редакций | Показывать оба значения, даты документов и источник, который изменяет прежнее условие. Передавать неразрешённые расхождения на ручную проверку. | Считать пропущенные расхождения и ошибки выбора редакции на размеченных примерах. |
| Управление длительными задачами | Добавить отмену, повтор без дублирования запуска и уведомление о готовности. Показывать число запросов и причины остановки. | Проверять отмену и восстановление при сбое, измерять время ответа и долю завершённых запусков. |
| Регрессии качества | Собрать свой эталон из типичных вопросов и сложных примеров. Сравнивать прямой режим и проверку при изменениях модели или промпта. | Измерять долю подтверждённых ответов, ложных утверждений и осторожных отказов отдельно. |

Для первого пилота проверьте правильную цитату, выдуманную цитату, неподтверждённое число, конфликт двух файлов и неполное чтение. В пилоте с несколькими пользователями добавьте проверку доступа к чужому `run_id` и повтор одного запроса после сетевого сбоя.
